# Codex Reasoning Router：Minimal-3 三任务对比报告

日期：2026-08-24

数据集：`minimal-3@0.2.0`

## 技术摘要

本次探针对比了两种 `dsh-codex-reasoning-router` 配置：

1. **混合配置**：根 Agent 为 Luna max，brain 为 Sol medium，coordinator 和 worker 为 Luna max。
2. **全 Luna 配置**：根 Agent、brain、coordinator 和 worker 均为 Luna max。

两种配置在 M1、M2、M3 上均达到 `ShipReady`，平均完成度分别为 99.37 和 99.81。M1 与 M3 的两组结果都是 100 分；只有 M2 出现 1.32 分差异。因此，`minimal-3` 对本次两种强配置的**交付质量区分度已经接近饱和**，但仍然显示出明显的运行效率和收敛路径差异。

混合配置完成三题共耗时 54.45 分钟，全 Luna 配置耗时 65.44 分钟；全 Luna 总耗时高 20.2%。不过差异方向并不稳定：全 Luna 在 M1 更快，M2 两组都达到时间上限，而混合配置在 M3 快 15.57 分钟。每个任务和配置仅运行一次，因此不能把总体耗时差解释为稳定的模型优势。

本报告按实验约定省略 token 数量。运行使用 Codex 订阅，文中 API 价格仅用于说明模型资源的相对价值，不代表本次实验的实际支出。

原始机器记录保留在本地 `results/codex-router-probe-20260824.json`，其中包含本报告不公开的 token 与 session 元数据，因此不随报告提交。

## 分任务解释

### M1 没有质量差异，全 Luna 更快

两种配置都完整通过基本行为、预订幂等、取消幂等、持久化卫生以及重启与不变量检查，完成分均为 100。全 Luna 比混合配置快 4.58 分钟。该结果说明，在这一轮中调用 Sol brain 没有带来 evaluator 可见的质量提升。

### M2 产生了唯一的质量差，但两组都未在时限内主动结束

两种配置都生成了可行且确定性的调度器并达到 `ShipReady`。全 Luna 的完成分为 99.43，混合配置为 98.11；差异来自优化目标质量，而不是可行性或 API 合约失败。

两组进程都由 1560 秒外层保护时限终止，并对终止时的工作区快照进行外部评估。按照本仓库的指标协议，模型超时但留下有效、高质量产物属于有效运行结果，不能标记为基础设施无效。

### M3 没有质量差异，混合配置显著更快

两种配置均完整通过状态机、输入合约、lease 语义、幂等、重试与 dead-letter、重启与持久化检查，完成分均为 100。混合配置比全 Luna 快 15.57 分钟，是本轮最大的运行效率差异。

## Sol brain 的实际覆盖有限

为验证插件的三条角色路由，每次正式运行都要求 brain、coordinator 和 worker 至少成功调用一次。六次运行中的所有指定角色调用均成功。

但是，在三次混合配置运行中，Sol brain 每题只调用一次，合计 3 次；混合配置总共有 182 次模型请求。因此，这轮实验主要测量的是“Luna 主流程加少量 Sol 咨询”，没有充分测量 Sol 持续承担规划、诊断和重规划时的价值。

OpenAI 在 2026-08-24 的官方 API 模型对比页中列出的价格为：Sol 输入、缓存输入和输出分别为每百万 token 4、0.40 和 20 美元；Luna 分别为 0.20、0.02 和 1.20 美元。Sol 的输入与缓存输入单价约为 Luna 的 20 倍，输出约为 16.7 倍。由于本次使用 Codex 订阅，这些价格只能作为 API 等价的资源稀缺性参考，不能当作实际账单。[OpenAI 模型价格](https://developers.openai.com/api/docs/models/compare)

基于本轮结果，暂时没有证据支持在简单或中等任务中普遍使用 Sol。更合理的下一步是让 Sol 只处理少数可能改变方案质量的关键节点，例如根因诊断、架构选择和失败后的重规划，并通过控制调用次数的消融实验验证其增量价值。

## 实验范围与方法

- 数据集：`minimal-3@0.2.0`，任务顺序固定为 M1、M2、M3。
- 每个任务、每种配置正式运行一次，共 6 次正式运行。
- 根 Agent 在两组中均为 `openai-codex/gpt-5.6-luna@max`。
- 混合组 brain 为 `openai-codex/gpt-5.6-sol@medium`；其余角色为 Luna max。
- 全 Luna 组所有角色均为 `openai-codex/gpt-5.6-luna@max`。
- 单题声明时限为 1500 秒，进程保护时限为 1560 秒。
- Agent 停止后才在外部运行私有 evaluator；evaluator 不在被测工作区中运行。
- 两次修复前 M1 校准运行和一次 worker smoke probe 不计入正式结果。
- benchmark commit：`f883de7f71c90b680e74e44d6c9145518a2bdb6e`。
- router 基线 commit：`e24157c5abdc74bd1fbb4234ad1267ac245cf21b`。
- router 工作区差异 SHA-256：`f4c8a2f5f2ba2e175ca0466bd7728115dda13b0b08c4a24bdd8be11c3b4489ce`。
- DSH：`0.1.1-rc.2`；Codex CLI：`0.149.0`。

## 限制与不确定性

1. **样本量不足。** 每个任务和配置只有一次运行，无法估计随机性、方差或统计显著性。
2. **运行顺序未随机化。** 固定顺序可能受到缓存、服务负载或机器状态影响。
3. **质量天花板明显。** 六次结果均为 ShipReady，四次为满分，限制了对强配置的质量排序能力。
4. **角色调用是人为约束。** 强制每个角色至少调用一次适合验证插件线路，但不能代表路由器自然选择的最优策略。
5. **Sol 暴露量很低。** 每题一次 brain 调用不足以评估 Sol 在长链路推理中的价值。
6. **耗时包含端到端等待。** `wall_time` 是用户可见总耗时，不等同于纯模型推理时间。
7. **这是公开开发探针。** `minimal-3` 适合迭代与回归，不应作为独立的密封配置选择证据。

## 建议的下一步

1. 保留 `minimal-3` 作为插件线路、ShipReady 和基本回归探针。
2. 新增一个 6 题左右的短时分层集合，包含 easy、medium、hard，每个难度至少两题，并把单题上限控制在 3–10 分钟。
3. 分开运行自然路由和受控消融：自然路由允许系统自行决定是否调用角色；受控消融固定 brain 的调用节点和次数，只替换 Sol/Luna。
4. 在 medium/hard 任务中安排至少两个会影响最终实现的 brain 决策点，使 Sol 的规划价值能传递到 evaluator。
5. 对最终候选配置预先声明重复次数并随机化任务顺序；保持完成质量与时间、订阅额度或成本分别报告。
